CORE ARCHITECTURE MAP

Status: CORE SYSTEM MAP
Purpose: Собрать в одну цельную схему ядро AliMind: как связаны данные, загрузка, поиск, форматирование, интерфейс бота, сайт и будущий AI.

1. Главная идея системы

AliMind больше не выглядит как “просто Telegram-бот”.

Его правильная архитектура уже такая:

единое ядро данных
→ единая логика загрузки и поиска
→ разные интерфейсы вывода

То есть проект должен расти не как набор случайных экранов, а как система, в которой одно ядро обслуживает несколько направлений:

Telegram-бот

сайт

поиск

AI-слой

будущие модули экосистемы

2. Центральный принцип

В центре AliMind должна стоять не кнопка, не handler и не Telegram.

В центре должен стоять объект.

То есть базовая сущность системы:

Object Card

И уже вокруг неё строится всё остальное.

3. Главная архитектурная цепочка

Вот зрелая схема AliMind:

Object Cards
↓
Object Registry
↓
Loader
↓
Normalized Internal Objects
↓
Search Layer
↓
Formatter / Presentation Layer
↓
Interfaces: Bot / Site / AI

Это и есть ядро всей системы.

4. Слой 1 — Object Cards
Где живёт

data/objects/

Что это такое

Карточки реальных объектов каталога.

Примеры:

мастер

кафе

спортзал

такси

агентство

салон

сервис

Роль

Карточка хранит сущность объекта:

кто это

что это

где это

чем полезен

как связаться

в каком статусе находится

Важное правило

Карточка не должна хранить Telegram-специфичную логику.

То есть не:

callback

inline button config

UI-костыли

А именно контентный объект.

5. Слой 2 — Object Registry
Где живёт

например: data/object_registry.json

Что это такое

Единый реестр объектов системы.

Роль

Registry отвечает не за содержание карточки, а за состояние объекта в системе.

Он знает:

существует ли объект

где лежит файл

опубликован ли

partner/free/draft/archived

legacy/new format

готов ли к сайту

готов ли к AI

Смысл

Это карта объектов, а не сами объекты.

6. Слой 3 — Loader
Где живёт

bot/core/loader.py

Роль

Loader — это входные ворота данных.

Он должен:

читать registry

загружать нужные карточки

проверять целостность

понимать legacy и new format

приводить всё к единому внутреннему виду

Новый смысл

Loader больше не просто “открывает JSON”,
а решает:

что система имеет право считать валидным объектом

7. Слой 4 — Normalized Internal Objects
Что это такое

Единый внутренний формат объектов после загрузки.

Зачем нужен

Чтобы вся остальная система не думала:

это старая карточка или новая

photo или media.cover_image

description или full_description

Внутри системы объект уже должен выглядеть одинаково.

Это ключевой узел

Именно здесь хаос входных данных гасится до того, как попадёт в:

поиск

formatter

сайт

AI

8. Слой 5 — Search Layer
Где живёт

bot/core/search.py

Роль

Поиск по нормализованным объектам.

Он должен:

принимать запрос

нормализовать текст

искать по структурированным полям

ранжировать результаты

отдавать релевантные объекты

Не должен

читать JSON напрямую

знать про Telegram UI

строить карточки

Смысл

Search — это движок навигации по данным.

9. Слой 6 — Formatter / Presentation Layer
Где живёт

bot/core/formatter.py

Роль

Показывать объект пользователю в нужной форме.

Должен делать

полную карточку

краткий элемент списка

поисковый сниппет

позже — превью для сайта

Не должен делать

лечить сырые данные

читать файлы

принимать решения о публикации

управлять кнопками как бизнес-логикой

Смысл

Formatter отвечает только за представление, а не за данные.

10. Слой 7 — Interface Layer
Где живёт

bot/handlers/

Что включает

start.py

menu.py

city_today.py

emergency_contacts.py

favorites.py

recents.py

card_sender.py

Роль

Это слой пользовательского движения.

Он отвечает за:

вход в систему

маршруты

возвраты

выбор категории

открытие карточек

избранное

последние

действия пользователя

Важное правило

Handlers не должны становиться складом данных и костылей.
Они должны управлять потоком пользователя, а не подменять собой core.

11. Отдельная ветка — City Events Layer
Где живёт

bot/city_events/
data/events/

Что это такое

Отдельный тип данных, не каталог объектов.

Сюда относятся:

дежурные аптеки

отключения электричества

отключения воды

экстренные службы

Почему это отдельная ветка

Потому что это не постоянные карточки бизнеса, а событийная / оперативная информация.

Архитектурно

Эта ветка должна жить рядом с каталогом, но не смешиваться с ним.

12. Telegram Bot как интерфейс, а не центр мира

Это очень важный сдвиг.

Сейчас визуально кажется, что проект = бот.

Но архитектурно правильнее так:

бот — это один из интерфейсов ядра

То есть Telegram — не хозяин системы, а один из способов доступа к данным.

Это сильное и зрелое мышление.

13. Website Layer
Что это будет

Сайт должен подключаться не к хаосу файлов, а к нормализованному слою.

Сайт сможет использовать:

объекты каталога

slug

категории

описания

контакты

районы

изображения

Что это даст

карточки объектов

страницы категорий

поиск по сайту

SEO-страницы

индексацию Google

Принцип

Сайт не должен жить отдельной жизнью от бота.
Он должен брать те же сущности.

14. AI Layer
Что это будет

AI-слой не должен фантазировать по пустоте.

Он должен работать через:

нормализованные объекты

поиск

чистые факты

контролируемые источники

Модель

user query → search/retrieval → object facts → AI answer
