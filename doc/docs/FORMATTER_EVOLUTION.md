FORMATTER EVOLUTION PLAN

Status: PRESENTATION LAYER PLAN
Purpose: Показать, как должен развиваться formatter.py, чтобы он отвечал только за представление объекта, а не тащил на себе хаос данных, бизнес-логику и Telegram-зависимые костыли.

1. Текущая роль formatter

На раннем этапе formatter.py обычно делает простую вещь:

берёт объект

собирает текст карточки

подготавливает вывод для Telegram

Для старта это нормально.
Но потом почти всегда появляется риск:

formatter начинает не просто “форматировать”, а латать дыры данных.

И вот это уже опасно.

2. Главная проблема, которую надо не допустить

Если formatter.py начнёт:

сам догадываться о структуре старых и новых карточек

искать, где лежит фото

решать, есть ли у объекта партнёрский статус

понимать callback-кнопки

разруливать логику, чего показывать, а чего нет

то он перестанет быть formatter и превратится в хаотичный узел.

А это потом ломает:

карточки

списки

сайт

поиск

поддержку проекта

3. Новый смысл formatter

formatter.py должен отвечать только на один вопрос:

“Как показать уже нормализованный объект пользователю?”

Не:

что грузить

как валидировать

где лежат данные

какой формат legacy

можно ли публиковать

А только:

как красиво, коротко и понятно это показать

4. Правильное разделение ролей
Loader

читает

проверяет

нормализует

Formatter

превращает нормализованный объект в представление

Это железное разделение.

5. Эволюция formatter по этапам
STAGE 1
RAW TELEGRAM FORMATTER
Модель

raw json → telegram text

На этом этапе formatter часто работает почти напрямую с JSON.

Что происходит

берёт поля как есть

собирает текст

может зависеть от структуры карточки

Плюс

быстро оживляет бота

Минус

любое изменение формата карточки начинает бить по formatter

STAGE 2
SAFE TELEGRAM FORMATTER

На этом этапе formatter становится аккуратнее.

Что добавляется

защита от пустых полей

корректная обработка отсутствующих данных

отсутствие падений из-за None

нейтральный показ неполной карточки

Задача

Пользователь не должен видеть ломку, даже если данные неполные.

STAGE 3
NORMALIZED OBJECT FORMATTER

Вот это уже правильный уровень.

Модель

normalized internal object → telegram card

Formatter получает не сырой JSON, а уже нормализованный объект.

Что это даёт

Formatter больше не думает:

это legacy или new

photo или media.cover_image

description или full_description

Он работает только с единым понятным набором полей.

Это главный архитектурный перелом.

6. Что должен уметь зрелый formatter

Он должен уметь собирать несколько типов представления.

Не один “универсальный текст на всё”, а разные форматы показа.

6.1 Полная карточка объекта

Для открытия одного объекта.

Содержит:

имя

headline

краткое или полное описание

услуги

локацию

контакты

статус при необходимости

6.2 Короткая карточка для списка

Для результатов категории, поиска, избранного, последних.

Содержит:

имя

краткое пояснение

район / категория

минимум визуального шума

6.3 Поисковый сниппет

Для быстрых результатов поиска.

Содержит:

имя

краткое совпадение по смыслу

одну полезную строку

6.4 Спец-формат для партнёров

Если объект партнёрский, formatter может добавить мягкий признак статуса.

Но без агрессии и без превращения карточки в рекламу.

7. Что formatter не должен делать

Это надо закрепить жёстко.

Formatter не должен:

читать файлы

лазить по папкам

решать, опубликован объект или нет

понимать registry

формировать callback как бизнес-логику

определять, кому можно отправлять заявки

искать объект в данных

хранить состояние пользователя

принимать архитектурные решения за loader

Если он это делает — роли уже смешались.

8. Где должна жить логика кнопок

Очень важный момент.

Кнопки Telegram — это не задача formatter в полном смысле.

Правильное разделение такое:

Formatter

делает текстовое представление карточки

UI / handler layer

решает:

какие кнопки показать

какой callback повесить

куда ведёт кнопка

когда показать “в избранное”

когда показать “оставить запрос”

То есть formatter может максимум вернуть сигналы, что объект:

партнёрский

принимает запросы

имеет контакты

Но не должен сам строить поведение интерфейса как ядро логики.

9. Что должно входить в форматирование карточки

Для полной карточки у formatter должны быть опорные блоки:

заголовок

подзаголовок / headline

краткое описание

список услуг

район / город

контакты

дополнительные признаки

Но всё это — на основе уже нормализованных данных.

10. Принцип вывода

Есть важная вещь: карточка не должна быть перегружена.

Formatter должен придерживаться принципа:

сначала быстрое понимание, потом детали

То есть пользователь должен сразу увидеть:

кто это

что делает

где находится

как связаться

А не тонуть в полотне текста.

11. Стиль formatter для AliMind

С учётом духа проекта formatter должен быть:

спокойный

ясный

без рекламного крика

без спама эмодзи

без лишнего шума

mobile-first

Карточка должна читаться за несколько секунд с телефона.

12. Что formatter должен получать от loader

Идеально formatter должен получать уже единый объект примерно такого уровня:

id

name

headline

short_description

full_description

category

status

location

contacts

services

languages

cover_image

accept_requests

То есть formatter не должен разбирать вложенную историческую кашу.

13. Эволюция по видам представления

Нормальный рост formatter должен идти не “одна функция на всё”, а по отдельным задачам представления.

Шаг 1

формирование полной Telegram-карточки

Шаг 2

формирование строк для списков

Шаг 3

формирование выдачи для поиска

Шаг 4

формирование короткого preview для сайта

Шаг 5

формирование полного текста для страницы объекта

Это не значит, что всё надо делать прямо сейчас.
Это значит, что formatter должен расти как слой представления, а не как случайный набор строк.

14. Зрелая схема formatter

Правильная модель такая:

Normalized Object → Formatter → Presentation Payload

Где Presentation Payload для Telegram может включать:

текст карточки

подпись

короткую строку для списка

А для сайта позже:

title

excerpt

body

meta blocks

То есть formatter может со временем стать слоем представления для разных интерфейсов, но только при условии, что данные уже нормализованы до него.

15. Риск, которого надо избежать

Самый опасный сценарий:

loader слабый

formatter “спасает”

handler добавляет свои костыли

search отдельно догадывается о данных

сайт потом изобретает ещё один формат

Вот это путь к распаду системы.

Правильный путь:

loader очищает вход

formatter показывает

handlers управляют навигацией

site layer использует те же сущности

16. Практическая линия развития для AliMind
PHASE 1

Оставить текущий formatter рабочим

PHASE 2

Убрать из formatter догадки о сырых форматах, когда loader начнёт нормализовать

PHASE 3

Разделить типы представления:

full card

list item

search item

PHASE 4

Убрать Telegram-специфичную бизнес-логику из formatter

PHASE 5

Подготовить formatter как нейтральный presentation-layer для бота и сайта

17. Что это даст проекту
Для бота

чище карточки

меньше костылей

проще поддержка

Для loader

чёткая граница ответственности

Для сайта

можно будет использовать те же объекты без нового хаоса

Для AI

AI не будет питаться телеграм-разметкой и мусорными строками

18. Куда реально должен прийти formatter

Итоговая цель такая:

formatter.py — это не “место, где кое-как собирается текст”,
а контролируемый слой представления нормализованных объектов.

Это уже зрелый смысл модуля.

20. Вывод

FORMATTER EVOLUTION PLAN фиксирует простое и важное правило:

formatter не должен лечить данные и не должен принимать архитектурные решения за другие модули.

Его задача:
взять уже чистый объект и показать его пользователю ясно, спокойно и удобно.

21. Фиксация

FORMATTER RULE v1
formatter.py развивается от сборщика сырого Telegram-текста к слою представления нормализованных объектов:

normalized object → presentation format
