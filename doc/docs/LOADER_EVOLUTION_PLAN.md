LOADER EVOLUTION PLAN

Status: CORE EVOLUTION PLAN
Purpose: Показать, как должен измениться loader.py, чтобы система перешла от простого чтения JSON к управляемой загрузке объектов для бота, сайта, поиска и AI — без поломки текущего бота.

1. Текущая роль loader

Сейчас loader.py у вас, по сути, делает базовую вещь:

находит JSON-файлы

читает их

превращает в объекты

отдаёт дальше системе

Для раннего этапа это было правильно.
Но на росте этого уже мало.

Потому что loader начинает быть не просто “читателем файлов”, а входными воротами слоя данных.

2. Новый смысл loader

Новый loader.py должен отвечать уже не только на вопрос:

“что лежит в папке?”

а на вопрос:

“что система имеет право считать валидным объектом?”

Это огромная разница.

3. К чему должен прийти loader

Итоговая цель такая:

Loader должен стать нормализатором и контролёром входа данных.

То есть он должен:

знать, какие объекты грузить

уметь читать старый и новый формат

приводить всё к единому внутреннему виду

отбрасывать мусор и сломанные карточки

отдавать системе уже понятные объекты

4. Эволюция loader по этапам
STAGE 1
FILE READER LOADER
Модель

folder → json files → objects

Что делает

читает все JSON из data/objects/

просто загружает их

Плюсы

быстро

просто

удобно для MVP

Минусы

нет контроля публикации

нет контроля формата

нет статусов

нет разграничения: грузить всё или не всё

Это стартовая стадия.

STAGE 2
SAFE FILE LOADER

На этом этапе loader остаётся файловым, но становится аккуратнее.

Что добавляется

защита от битых JSON

пропуск пустых файлов

базовая валидация обязательных полей

логирование ошибок загрузки

Задача

Не ломать весь бот из-за одной кривой карточки.

Результат

Loader уже не наивный, а безопасный.

STAGE 3
FORMAT-AWARE LOADER

Это первый реально важный шаг.

Loader начинает понимать, что в системе есть:

legacy карточки

transitional карточки

new standard карточки

Что он должен уметь

Если карточка старая:

читать description

читать photo

терпеть старую структуру

Если карточка новая:

читать short_description

читать full_description

читать media

читать contacts

читать features

Смысл

Не заставлять весь бот и сайт разбираться в хаосе форматов.

STAGE 4
NORMALIZING LOADER

Это центральный этап всей эволюции.

Loader должен уметь делать не просто “read”, а normalize.

То есть на выходе внутри системы должен появляться единый внутренний объект, даже если карточки на входе разные.

5. Что такое нормализация

Допустим, есть старая карточка:

{
  "id": "BEAUTY_OLESYA",
  "name": "Olesya — мастер по волосам",
  "description": "Профессиональный женский мастер...",
  "photo": "partners/Olesya.jpg"
}

И новая карточка:

{
  "id": "BEAUTY_OLESYA",
  "name": "Olesya",
  "headline": "Мастер по волосам в Алании",
  "short_description": "Женский мастер по волосам...",
  "full_description": "Профессиональный женский мастер...",
  "media": {
    "cover_image": "partners/Olesya.jpg"
  }
}

Для системы на выходе должно получиться что-то однотипное:

id

name

headline

short_description

full_description

cover_image

contacts

location

features

Даже если часть полей заполнена из legacy-источника.

6. Главная идея

Не formatter, не search, не site layer должны лечить хаос.
Это обязанность loader.

Вот где реальная архитектурная зрелость.

7. Следующий этап
STAGE 5
REGISTRY-AWARE LOADER

После этого loader должен научиться работать через object_registry.json.

То есть уже не так:

“вижу файл — загружаю”

а так:

“registry разрешил — загружаю”

Что это даёт

Loader начинает учитывать:

is_published

status

schema_version

compatibility

source_type

И может, например:

не грузить archived

не отдавать draft

отделять legacy

знать, что можно отдавать сайту, а что нет

8. Правильная схема работы зрелого loader

Нормальная логика должна стать такой:

Шаг 1

прочитать registry

Шаг 2

взять список разрешённых объектов

Шаг 3

открыть соответствующие JSON-файлы

Шаг 4

провести базовую проверку

Шаг 5

нормализовать в единый внутренний объект

Шаг 6

вернуть системе уже чистый набор объектов

9. Внутренний формат объекта

Это очень важная точка.

Нужно закрепить, что loader возвращает не “как было в JSON”, а как надо системе.

То есть внутри Python дальше должен жить уже единый объект.

Не обязательно прямо сейчас делать сложные dataclass-модели.
Но логика должна быть именно такой.

Например внутренне объект должен иметь такие поля:

id

slug

category

name

headline

short_description

full_description

status

location

contacts

services

languages

cover_image

gallery

accept_requests

is_published

schema_version

Это уже похоже на системную сущность, а не на сырой JSON.

10. Что не должен делать loader

Есть важная граница.

Loader не должен:

строить Telegram кнопки

формировать HTML/Markdown текст

решать UX навигации

заниматься поисковой выдачей как интерфейсом

рисовать карточку для сайта

Это не его роль.

Loader должен:

читать

проверять

нормализовать

отдавать

11. Какие функции логично появятся

Не кодом, а по смыслу.

1. Загрузка registry

Функция чтения object_registry.json

2. Загрузка одной карточки

Чтение конкретного JSON по пути

3. Определение формата карточки

Понять: legacy / new / broken

4. Нормализация карточки

Приведение к внутреннему виду

5. Массовая загрузка объектов

Собрать набор объектов по правилам

6. Фильтрация по состоянию

Например:

только опубликованные

только партнёры

только category=beauty

12. Что это даст formatter.py

Formatter перестанет гадать:

есть ли photo или уже media.cover_image

есть ли description или уже short_description

где лежит contact

откуда брать headline

Он просто будет получать уже готовый внутренний объект.

Это сильно чистит код.

13. Что это даст search.py

Поиск перестанет искать по хаотичным ключам из разных эпох.

Он сможет искать по нормализованным полям:

name

headline

services

district

short_description

full_description

Это даст устойчивость и точность.

14. Что это даст сайту

Сайт не должен лезть в сырые JSON.
Он должен брать уже понятный слой данных.

Именно loader либо отдельный export-layer должен давать сайту:

slug

title

preview

full text

image

contacts

district

category

То есть сайт строится уже на очищенном фундаменте.

15. Что это даст AI

AI-слой сможет работать по нормализованным, проверенным объектам, а не по мусору типа:

callback

actions

куски телеграм-разметки

полусырые текстовые поля

Это критично, если вы хотите, чтобы AI отвечал честно и структурно.

16. Переход без боли

Очень важно: loader нельзя переписывать “в один удар”.

Правильная линия такая:

PHASE 1

Оставить текущую загрузку, но добавить safe-read

PHASE 2

Добавить понимание legacy и new format

PHASE 3

Добавить нормализацию на выходе

PHASE 4

Подключить registry как опцию

PHASE 5

Сделать registry основным источником загрузки

Это мягкая эволюция, а не революция.

17. Архитектурный рост loader

Вот честная карта роста:

Было

loader = читатель JSON

Станет

loader = gatekeeper + normalizer

Это и есть зрелый смысл этого модуля.

18. Практический итог для AliMind

Для вашего проекта loader.py становится одним из ключевых файлов всей будущей системы.

Потому что он будет соединять:

старый каталог

новый стандарт карточек

registry

бот

сайт

поиск

AI

Если loader сделать правильно, вы потом не будете каждые две недели переделывать весь проект.

19. Финальная схема

Object Cards
↓
Object Registry
↓
Loader
↓
Normalized Internal Objects
↓
Bot / Site / Search / AI

Вот это и есть зрелая схема работы.

20. Вывод

LOADER EVOLUTION PLAN фиксирует новую роль loader.py:

он больше не просто читает JSON-файлы,
он становится контролируемым входом в слой данных.

То есть именно loader должен сделать так, чтобы:

бот не ломался от старых карточек

сайт не зависел от Telegram-формата

поиск работал по единым полям

AI получал чистые объекты

миграция шла мягко и без хаоса

21. Фиксация

LOADER RULE v1
loader.py развивается от простого чтения JSON к роли управляемого загрузчика и нормализатора объектов:

read → validate → detect format → normalize → expose to system
